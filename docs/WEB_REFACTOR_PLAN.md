# TripLedger 網頁版重構範圍

日期：2026-09-22。此文件區分使用者已確認的需求與依程式碼盤點提出的建議；尚未實作網頁版。

## 已確認需求

1. 從原本手機 App 轉為網頁應用，手機使用優先，同時保留電腦版。
2. 記帳／分帳基本概念維持，但可以大幅調整架構與操作流程。
3. 第一階段供內部測試，沒有付費內容。
4. 預留公開服務與付費版本的擴充空間。
5. 舊版只有測試資料，可重新設計資料結構，無正式資料遷移需求。
6. 使用者認為原 GCP 部署初期成本過高，已有一台主機／NAS 可作備用資源。目前優先評估完全使用或部分使用 Sites；不以取得主機規格為評估前提。

## 建議技術方向

網頁前端建議採 React + TypeScript，舊 `apps/mobile` 先保留為行為與畫面參考。後端依 Sites 評估結果選擇：完全使用 Sites 時，將既有業務規則移植至相容的伺服器執行環境與資料存取層；部分使用 Sites 時，沿用並整理 `apps/api` 的 NestJS／Prisma／PostgreSQL。目前未選定託管路線，尚未安裝套件或變更現有架構。

網頁應用以瀏覽器操作為基礎，可加入 PWA 安裝入口，讓支援的裝置能加入主畫面。PWA 安裝能力與完整離線記帳是兩個範圍；第一階段建議先完成可靠的線上資料儲存。各平台安裝方式不同，不能以一個安裝提示代表所有瀏覽器。[MDN 安裝條件](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable)

Flutter 本身適合互動型 Web App，並非必須改用其他技術；官方也指出網頁上的原生檔案 API、`Platform.is...` 及平台匯入需要適配。[Flutter Web FAQ](https://docs.flutter.dev/platform-integration/web/faq)

本專案選擇重建網頁前端的理由來自實際程式：

- `main.dart` 在 `runApp` 前直接初始化 LINE SDK；啟動後還初始化手機廣告與 App Store／Google Play 內購。
- `login_page.dart:565` 直接使用 `Platform.isIOS`；不能只因存在 `web/` 就認定登入流程已適配瀏覽器。
- 收據流程將照片路徑轉 `dart:io File`，接到本機 OCR、圖片壓縮與檔案上傳；瀏覽器需改為 File／Blob／bytes 的資料流。
- 畫面以 375 × 812 的手機設計基準與大型頁面為主；電腦版仍需重新安排導覽、列表與表單。
- 邀請 QR 目前使用 `tripledger://join`，網頁版需改為 HTTPS 邀請網址，並保留登入後回到邀請流程的能力。
- 這次允許大幅重構且主要平台轉為網頁，重新建立瀏覽器表單、路由與響應式版面較符合目標；代價是 Dart 畫面需重寫，不能自動轉換。

React + TypeScript 的工具支援可參考 [React TypeScript 文件](https://react.dev/learn/typescript)。實作時應使用成熟的路由及伺服器資料管理方案，避免自行拼出不一致的載入、快取與錯誤處理；SSR／公開介紹頁需求也應與登入後的記帳應用分別評估。[React 建置與架構取捨](https://react.dev/learn/build-a-react-app-from-scratch)

## 第一階段建議產品範圍

| 範圍 | 內測版目標 |
| --- | --- |
| 使用入口 | 受控的測試帳號或允許名單；每位測試者有自己的身份，能驗證多人分帳與權限。登入供應商於實作前確定。 |
| 旅程／群組 | 建立、編輯、成員邀請、虛擬參與者；保留既有分帳情境。 |
| 記帳 | 新增、編輯、刪除、列表與明細；付款者、參與者、分類、日期、幣別。 |
| 分攤 | 以既有五種分攤為功能盤點基準，先完成手動記帳的完整流程，再補齊進階表單。 |
| 結算 | 顯示正確剩餘應收／應付；還款確認後立即反映在餘額與建議中。 |
| 手機介面 | 適合觸控與單欄操作；主要記帳動作容易觸及，鍵盤開啟時仍可完成表單。 |
| 電腦介面 | 同一份帳務資料，搭配較寬的列表、詳情與表單配置，支援鍵盤操作。 |
| 收據與 OCR | 保留在重構盤點；安排於手動記帳流程穩定後。優先瀏覽器拍照／選檔上傳，接後端辨識與人工確認。 |
| 商業內容 | 內測不顯示價格、升級、購買、廣告，也不要求測試者透過購買解鎖功能。 |

以上為實作排序建議，不代表已決定永久移除尚未列入第一批畫面的舊功能。

## 保留未來付費版的方式

將登入身份、群組資料存取權限、功能權益與服務用量分開：

- **資料存取權限**：是否能讀取／編輯這個群組的帳務，始終由後端驗證。
- **功能權益**：由集中式權益服務判斷某使用者／群組能否使用功能。內測採設定明確授權所需功能，日後可由方案或訂閱提供權益。
- **用量控管**：OCR 等外部服務仍可有技術額度與節流，但內測不導向購買或升級。
- **付款整合**：後續再選擇網頁付款供應商，處理訂閱狀態與事件；首版不建立空殼結帳流程。

目前 `premiumExpiresAt` 判斷散落於帳單、旅程、虛擬成員及結算服務；OCR 無限額又綁在去廣告權益。只隱藏前端付費按鈕不能完成「無付費內容」。`PremiumGuard` 檔案存在但未找到套用處，實際限制必須逐一從服務中抽出；調整權益時必須保留成員與資料存取驗證。

內測政策只應作用於獨立的內測環境。保留擴充點不代表要預先實作整套訂閱、定價與帳務系統。

## 瀏覽器整合需要補齊

- 既有 API 使用 Bearer access token，登入／刷新以 JSON 傳遞 token，沒有完成的瀏覽器 cookie session 契約。實作時應先選定同源代理、登入跳轉及 session 策略，並處理 token 刷新失敗與並行請求。
- 正式設定缺少 `CORS_ORIGIN` 時會拒絕跨站請求，Web 部署必須明確設定來源或使用同源 API 路徑。
- 現有 Demo 登入是共用審核帳號，不能代表多人內測的個別身份。站內通知與瀏覽器推播應分開安排；首批流程不依賴原生 FCM、本機通知與商店 SDK。

## 資料與帳務重構原則

- 新資料結構可重新設計，使用獨立開發／內測資料庫；本文件不包含刪除或重置既有資料庫的操作。
- 區分登入帳號、群組成員資格與財務參與者，避免虛擬／正式／離開成員使用不同的計算分支。
- 統一金額精度、分攤總和與尾差分配；所有分攤合計必須等於帳單金額。
- 明確保存帳單匯率與基準幣；修改備註不應悄悄改變歷史債務。
- 帳單主資料與分攤以同一資料庫交易更新。
- 餘額計算納入已確認還款，並明確處理取消、部分還款與多幣別。
- 核心規則獨立於前端畫面、通知、OCR 與未來付費策略。

## 建議執行順序與完成條件

1. **確定新版流程與頁面**：先定義登入、群組、帳單、成員與結算的主要操作；產出手機與桌機版面規劃。
2. **建立重構基礎**：在開發分支新增網頁前端與隔離的測試環境，選定登入策略，建立 API 契約；修正登入綁定與帳務規則問題。
3. **交付第一條完整流程**：兩位測試者登入、加入同一群組、新增／編輯帳單、分攤、確認還款，重新整理後資料仍正確。
4. **補齊體驗與周邊功能**：進階分攤、多幣別案例、統計、收據上傳／OCR；加入需要的 PWA 安裝體驗。
5. **內測驗收**：手機與桌機浏览器操作、資料隔離、錯誤回饋、金額一致性、還款後餘額、無付費入口與廣告。

建議測試代表寬度為 360／390／768／1280px，並包含手機 Safari、Android Chrome 及桌機瀏覽器。此為未來驗收清單，本次尚未實跑。

現況盤點與 Git 基準見 [REFACTOR_BASELINE.md](REFACTOR_BASELINE.md)。

## 部署方向補充：優先評估 Sites

依使用者最新指示，主要評估「完全使用 Sites」及「Sites 前端＋外部後端」。已知有主機／NAS 即可，不再蒐集設備規格，也不預設全面自架是主線。此為方案評估，沒有建立 Site、發布服務、連線 NAS 或操作 GCP 資源。

| 路線 | 本專案的改動與取捨 |
| --- | --- |
| 全部使用 Sites | 網頁、API、D1 資料庫與 R2 檔案儲存放在 Sites；可減少自行維運的元件。需移植現有 Node 常駐服務與 Prisma／PostgreSQL 資料存取，重新驗證帳務交易與精度，不是直接上傳現有 Docker image。 |
| 部分使用 Sites | Sites 託管前端，NestJS／PostgreSQL 留在外部主機；較能沿用既有後端。須提供可達的 HTTPS API，處理登入與跨來源設定，仍需維運後端；主機離線時帳務服務仍會中斷。 |
| 全部自架（備案） | 保留可攜性選項，目前不作優先評估，也不需要先提供 NAS 規格。 |

### 兩條主線的判斷依據

| 評估面向 | 全部使用 Sites | 部分使用 Sites |
| --- | --- | --- |
| 首版內測 | 沒有正式舊資料或金流，可直接設計新資料模型，適合先驗證平台適配性。 | 能沿用經修正的 API，降低後端移植量。 |
| 記帳正確性 | 需驗證 D1 上的交易、併發、金額儲存、尾差與結算規則。 | 需修正現有帳務問題，但可保留 PostgreSQL 資料庫能力。 |
| 登入與多人協作 | 確認測試者登入／邀請方式，以及未來大眾登入路徑；平台存取權不能代替群組帳務權限。 | 外部 API 自行驗證身份與成員資格；不能直接信任瀏覽器轉送的身份資訊。 |
| OCR 與圖片 | 評估 R2 及外部辨識 HTTP API；外部服務的費用仍另計。 | 沿用或改寫既有圖片／OCR adapter；外部服務的費用仍另計。 |
| 公開使用 | 核對帳號可用的公開設定、網域、用量及資料匯出／搬遷方式。 | Sites 的前端限制仍需核對，後端容量與資料可獨立調整。 |
| 未來付費 | 平台用途限制與訂閱支援尚待核實，不能預先承諾。 | 後端可保留付款整合邊界，但把後端外移不代表 Sites 前端的用途限制自動消失。 |

建議先驗證全 Sites 能否完成「兩個帳號加入同一群組 → 記帳 → 分攤 → 還款 → 重整後資料正確」；若登入、帳務交易、用量或未來產品條件不符，再採部分 Sites。這是評估順序，不是已決定改寫全部後端或授權發布原型。

使用者另要求評估「先全部使用 Sites，若日後託管費用增加，再轉到 NAS／Windows」。判斷為有條件可行，完整方案見 [SITES_EXIT_STRATEGY.md](SITES_EXIT_STRATEGY.md)；首版增加原始碼保留、平台介面隔離、完整資料／附件匯出、帳戶身份映射與獨立還原演練的驗收。不能以 Sites 開發預覽可執行，就當成已證明脫離平台後可以正式自架。

Sites 能託管網站與 Web App，並提供 D1／R2；支援 HTTP(S)，不支援原始 TCP，因此現有 Prisma PostgreSQL 直連方式不能原樣搬入。Sites 的發布目標是平台代管服務，不是把容器部署到使用者 NAS。[官方 Sites 文件](https://learn.chatgpt.com/docs/sites)

Sites 公開測試期間包含於符合資格的 ChatGPT 方案，仍受帳號、地區、工作區與使用限制影響，不能當成永久無限免費主機。這次只確認目前帳號能成功讀取 Sites 列表，沒有確認建立／部署額度或特定網域可用性。[官方費用說明](https://learn.chatgpt.com/docs/pricing#how-much-does-sites-cost)

官方亦列出金融交易與付款卡資料的用途限制。分帳紀錄和真正收付款需要區分；未來要在 Sites 承載訂閱結帳或實際轉帳時，需重新核對當時規範與平台支援，不能把「可託管網頁」當作已確認金流適用。[用途限制](https://learn.chatgpt.com/docs/sites#understand-limits-and-unsupported-uses)

### 外部主機備案參考（暫不展開設備規劃）

```text
手機／電腦
    ↓ HTTPS（內測採受控入口）
主機／NAS：反向代理與網頁 → NestJS API → PostgreSQL
                                  ↓
                           收據檔案儲存（選用）
```

- 使用 Docker Compose 管理 API、資料庫與網頁／反向代理；是否支援及映像架構須依主機確認。Compose 官方提供單機部署方式。[Docker 官方部署說明](https://docs.docker.com/compose/how-tos/production/)
- 小範圍內測可先使用區域網路／VPN；需要外部測試時，再選受控 HTTPS 入口。無固定公網 IP 可評估 Cloudflare Tunnel，其連線由主機向外建立；Tunnel 本身不會取代應用程式登入與權限。[Cloudflare Tunnel](https://developers.cloudflare.com/tunnel/)
- PostgreSQL 使用持久儲存，配合獨立備份；對外只提供網站入口，不公開資料庫埠或 NAS 管理介面。
- 原有 Compose 僅包含 PostgreSQL、Redis、pgAdmin，沒有 API／網站，不能直接視為完整上線方案。程式目前沒有實際使用 Redis，首版無須先加入。
- 現有 Dockerfile 可以作為自架起點；資料庫 migration 需獨立安排，不能假定 production image 內已有 Prisma CLI。

### 若採外部後端：GCP 與外部服務的處理

- Cloud Run 改由自架 API 容器取代；Cloud SQL 改接自架 PostgreSQL，調整 `DATABASE_URL`。
- Cloud Build／Secret Manager 改為自架部署流程及主機端秘密設定；前端改用部署設定或同源 `/api`。
- Google Vision OCR、Anthropic 品牌辨識、AWS S3 收據圖片、外部匯率 API 是另外的依賴；移走 API 主機不會自動移除它們的用量或費用。
- 若收據圖片改存 NAS／其他物件儲存，需要檔案儲存 adapter。現有 S3 程式把 AWS endpoint 與 URL 格式寫死，不能只替換金鑰。
- 若內測先不使用雲端辨識，應以明確功能開關停用，保留人工記帳；不要僅刪除憑證並期待自動停用。
- 實際節費額仍需原 GCP 帳單及自架電力／備份／網域成本；尚未取得帳單，因此未判定哪項是原費用主因。

只有選定外部主機路線、準備實際部署時，才需要確認設備與網路設定；目前 Sites 可行性評估不依賴這些資訊。
