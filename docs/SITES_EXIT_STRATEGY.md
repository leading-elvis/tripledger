# 先 Sites、後 NAS／Windows：可搬遷性評估

評估日期：2026-09-22。問題情境：先全部使用 Sites 進行內測；若未來 Sites 託管費用增加或限制不合適，再搬到既有 NAS／Windows 主機。以下保留架構評估；使用者後續已授權下一步，實作與驗證狀態見下方更新。

## 實作更新（2026-09-22）

已建立 `apps/web` 首版，具備受保護的單旅程完整 JSON 備份與匯入，包含實際收據 bytes／SHA-256、帳單分攤與已記錄還款。業務核心及前端共用，Sites 用 D1／R2／平台登入；獨立 Node 24 入口用 SQLite／同機檔案／單一管理者密碼。

已實測 **本機 Sites D1＋R2 → Windows Node＋SQLite＋檔案**，還原後旅伴、支出與還款 ID、餘額及收據 checksum 一致，重啟後仍持久化，重複匯入拒絕覆蓋。收據儲存 ID 於匯入時重新配置以避免覆寫。未驗證實體 NAS、公開多人帳號遷移或雲端已部署版本的還原。

已建立私人 Sites 專案，但官方發布工具檔案於工作階段中消失，故尚未完成發布。後續查核確認專案仍僅 owner 可存取、版本數為 0，未進行雲端還原測試。新版已保存到 GitHub 的 `refactor/web-sites-prototype` 分支，並從遠端重新 clone 驗證安裝、7 項測試、型別檢查與兩種建置。詳見 [首版操作與驗證說明](../apps/web/SELF_HOSTING.md)。下列「建議」包含後续公開版本需求，不代表首版全數完成。

## 結論

有條件可行，適合納入本專案路線。初版應同時具備可保留的原始碼、可替換的平台介面、完整匯出與可還原驗證。不能承諾把 Sites 的發布包直接複製到主機就能執行，也不能預設 Sites 已提供整站搬遷按鈕。

舊版只有測試資料，因此新版可從設計時建立這些邊界。若等到大量帳單、圖片與使用者都依賴平台後才處理，搬遷成本會提高。

## 已確認與尚未確認

- 已確認：Sites 可承載網頁／應用資料／檔案；官方與本機技能說明有本機原始碼、Git 版本、D1、R2 及平台登入的工作流。[Sites 官方文件](https://learn.chatgpt.com/docs/sites)
- 已確認：本機 Sites starter 的 `db/index.ts` 直接讀取 `cloudflare:workers` 的 D1 binding；`app/chatgpt-auth.ts` 依賴平台提供的身份 headers 與登入路徑。這些是需要隔離的具體平台依賴。
- 已確認：目前連接器的資料表讀取是有上限、可能截斷欄位內容的檢視工具，不能當成完整備份工具；版本與 Git 記錄也不等於生產資料備份。
- 尚未確認：Sites 帳號是否提供完整資料庫／R2 匯出介面、可否直接取得底層 Cloudflare 匯出權限、未來收費額及生效時間。
- D1 本身有官方匯出能力，但 Sites 代管資源不等於使用者自有 Cloudflare 資源，不能直接承諾能執行遠端 Wrangler 匯出。[D1 匯入／匯出](https://developers.cloudflare.com/d1/best-practices/import-export-data/)
- Sites 在公開測試期間包含於符合資格的 ChatGPT 方案；未來價格未由本次資料確認，不以永久免費作設計前提。[目前費用說明](https://learn.chatgpt.com/docs/pricing#how-much-does-sites-cost)

## 搬遷項目與相對工作量

下表是架構判斷，不是已實測的工時估算。

| 項目 | 初版的準備 | 搬遷時的工作 | 相對工作量 |
| --- | --- | --- | --- |
| 網頁介面 | 標準 React／TypeScript 元件；平台 API 集中在伺服器層 | 在自架執行環境重新建置，調整必要的框架／SSR 整合 | 低至中 |
| 分攤／結算規則 | 平台中立的業務函式與案例測試 | 沿用規則，核對在新環境的結果 | 低 |
| HTTP 後端 | 把 Sites Worker 入口與業務邏輯分開 | 新增一般 Node／容器服務入口，替換環境設定 | 中 |
| D1 資料庫 | 版本化業務資料格式，隔離 SQL 與資料庫存取 | 匯出、轉換、匯入 SQLite 或 PostgreSQL，驗證交易與資料關聯 | 中；換 PostgreSQL 另有型別／查詢轉換 |
| R2 收據圖片 | 使用 object key、檔案清單與校驗碼 | 搬出實際圖片 bytes，改接本地儲存或物件儲存 | 中，隨檔案量增加 |
| 登入帳號 | 內部 user ID 與平台身份映射分開 | 建立自架登入，讓使用者重新登入或受控綁定原帳號 | 中至高 |
| 網址／HTTPS | 網址與 OAuth 回呼可配置；若合適可使用自有網域 | 切換 DNS／入口、HTTPS、回呼與 Cookie 設定 | 中 |

Cloudflare Worker 有自己的執行 API 與 bindings；Node 相容性不代表其產物可直接作為一般 Node 服務或 Windows EXE 執行。應搬原始碼與資料，再建立適合目的地的執行入口。[Workers 執行介面](https://developers.cloudflare.com/workers/runtime-apis/)

## 初版必須保留的出口

### 1. 原始碼與平台邊界

原始碼、依賴鎖定檔、schema、migration、建置設定與操作說明留在可控的 Git 儲存庫。Sites 的發布版本與 GitHub 版本需能對應。程式碼備份與帳務／收據備份分開，使用者資料與秘密設定不放進公開程式碼儲存庫。

使用少量具體介面隔離三種依賴：資料庫、檔案儲存、登入身份。前端只呼叫 TripLedger 的功能 API；分攤／結算規則不直接讀取 D1、R2 或平台 headers。無須先建完兩套正式環境，但須保留一般 Node 可執行的路徑。

### 2. 能還原的資料與檔案匯出

優先評估官方可用的完整匯出；若未提供，實作應用層的受保護匯出與相對應匯入工具，實測後才視為搬遷出口。

建議匯出包包含：

- manifest：格式版本、程式版本、匯出時間／截止點、各資料表筆數及校驗資訊。
- 應用資料：使用者映射、參與者、群組、帳單、分攤、品項、還款、匯率快照、權益與用量；使用 JSONL 等可分頁、可續傳格式。
- 檔案 manifest 與實際內容：object key、所屬帳單、MIME、大小、SHA-256，加上完整收據圖片。

資料表 CSV、畫面截圖、圖片 URL 或 Git commit 都不足以代替上述備份。匯出應分頁／串流，避免把整個資料庫與所有收據塞進單次 Worker 記憶體；需按實際執行限制驗證。

R2 的 Worker API 提供讀取檔案與分頁列舉能力，可作為應用層下載的技術基礎；這不代表 Sites 帳號已提供 S3 金鑰或平台原生批次匯出。[R2 Workers API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/)

首版資料量較小時，可用受控停寫取得一致快照；更大資料量再設計版本／增量機制。資料匯出途中有新增或刪除時，不能把不同時間的分頁拼成完整帳務快照。

### 3. 可搬遷的帳務表示

- 金額使用明確幣別精度的最小單位整數，或受驗證的小數字串；跨 API／匯出不得以浮點值作唯一權威值。
- 保存原幣、基準幣、實際匯率、換算結果與時間；搬遷時不重新抓匯率或改算歷史交易。
- UUID、時間格式、enum、nullable 關係及陣列／JSON 欄位有明確契約，避免把 PostgreSQL schema 原樣當作 D1 schema。
- 分攤尾差、取消／已確認還款、退出／虛擬成員的歷史份額均有案例驗證。

### 4. 帳號可續用，登入狀態可重建

所有帳務關聯使用 TripLedger 自己的 user／participant ID；另存登入供應商、來源 Site 與外部 subject 的映射。平台 session、Cookie 與平台密碼不屬於可攜的帳務資料。

自架時可能需要重新登入及驗證帳號歸屬，再綁回原內部 ID。不可只憑使用者填入相同 email 自動認領舊帳戶。退出或匿名化的參與者仍需保留可核對的財務關聯。

### 5. 一次真實的還原演練

第一條完整分帳流程完成後，即把測試資料與圖片匯出到受控位置，還原到 Windows 本機的一般 Node／容器測試服務。驗證此服務不依賴 Sites 的登入 headers、D1、R2 或雲端資料。

這是驗證可搬遷性的方式，不是要求現在取得 NAS 規格或長期同時營運兩套服務。主要版本改動後再重做演練，定期備份留在 Sites 以外。

## 自架目的地

| 目的地 | 可行路線與界線 |
| --- | --- |
| Windows 桌面系統 | 符合官方支援條件時可用 Docker Desktop＋WSL2 執行 Linux 容器，或另建一般 Node 服務。Docker Desktop 不支援 Windows Server；屆時依實際 OS 選服務方式。[官方 Windows 支援](https://docs.docker.com/desktop/setup/install/windows-install/) |
| NAS | 支援容器、相應 CPU 架構與映像的設備可部署；不是任意 NAS 都適用。現在只保留目的地選項，不要求設備資訊。[Synology 適用機型與套件](https://www.synology.com/en-in/dsm/packages/ContainerManager) |
| SQLite | 可作單機自架資料庫候選；由後端集中讀寫同機磁碟，不讓 Windows 後端透過 NAS SMB 直接共用 SQLite 檔案。[SQLite 適用情境](https://sqlite.org/whentouse.html) |
| PostgreSQL | 適合保留原專案的資料庫方向，但從 D1 移入時仍需資料型別、查詢及 migration 調整。[PostgreSQL Windows 安裝](https://www.postgresql.org/download/windows/) |

## 真正切換時的流程

1. 部署目的地服務，先用較早備份演練，確認登入與儲存 adapter 可用。
2. 在 Sites 進入受控停寫狀態，匯出最後一致的資料與附件。
3. 匯入新環境；核對主鍵、關聯、筆數、各幣別金額、分攤合計、剩餘債務、權益及檔案校驗碼。
4. 使用多個測試帳號檢查資料隔離與權限，實際新增帳單和確認還款。
5. 切換入口／網域並重新登入；一次只讓一個環境接受正式寫入。
6. 保留受限存取的舊版與最後備份一段驗證期間，確認後再處理舊託管服務。若新站已接受寫入，回退前須遷回差異，不能直接切回舊快照。

完成條件：空白目的地可從備份還原，資料與檔案無缺漏，原帳戶可受控認回，正確業務結果一致；移除對 Sites 的連線後仍能使用核心流程。相同錯誤結果不算成功，因此現有已確認還款未扣餘額等問題要先修正。

## 成本判斷

這條路可延後自行維運成本，但需要在初版投入匯出／還原與平台隔離的開發成本。未來搬遷還有一次性工作，以及電力、網域、備份與維護等成本；外部 OCR／AI 費用不會因網站搬走而消失。

是否值得搬，屆時比較「Sites 額外月費」與「自架新增月成本＋搬遷一次性成本」。在不知道未來價目與資料規模時，不提供省錢比例或固定搬遷天數。

**建議採用條件：先通過小規模的完整匯出、獨立還原與帳號銜接演練，再把 Sites 當成可隨時退出的主部署管道。**
